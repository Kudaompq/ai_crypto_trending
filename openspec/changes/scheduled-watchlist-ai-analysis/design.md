## Context

动机和外部行为见 [proposal.md](proposal.md)，验收行为见 `ai-market-analysis-chat`、`scheduled-watchlist-analysis` 和 `wecom-market-alerts` 的增量规格。

当前后端以 Go/Gin 运行，`main` 已打开 PostgreSQL 并应用嵌入式 SQL 迁移。Watchlist 是服务端共享列表，数据库通过单例状态表存储，最多 100 个交易对。K 线模型包含 OHLCV；独立 OI 服务目前提供部分周期的历史数据。手动 AI 对话使用只收发普通 Chat Completions 文本的 provider，不支持工具调用。当前没有后台定时任务。

企微请求格式、纯文本限制、成功码校验和 webhook 脱敏参照 `/Users/kudaompq/Desktop/code/telegram-monitor/src/tgmonitor/notifier.py` 与其 `render.py`；该参考项目以每分钟 20 条和正文 2048 UTF-8 字节作为实现边界。

## Goals / Non-Goals

**Goals:**

- 在同一后端进程生命周期中运行可恢复、不会并发重叠的逐币扫描。
- 初始上下文包含价格、成交量和精简 OI 证据；AI 可通过受限只读工具按需深查当前币种的受支持周期。
- 保存每轮扫描的所有逐币最终输出和失败状态，并以成功投递记录驱动企微去重。
- 让企微请求超时、失败、分片和多实例部署都有可追踪行为。

**Non-Goals:**

- 不持久化页面手动聊天，也不保存模型工具调用的逐条中间消息。
- 不保存完整的 100 根 K 线或未经筛选的模型请求/响应原文；保存足以核对最终分析的结构化结果、证据摘要及来源时间。
- 不向 Binance Square 发布，不下单，不访问用户账户或其他交易对。
- 不补跑服务停机期间错过的每个小时扫描时段。

## Decisions

### 1. 将定时扫描作为后端后台服务

在数据库、Watchlist、市场上下文和模型 provider 初始化后启动扫描服务，并使用进程级取消上下文在服务关闭时停止调度和正在执行的工作。扫描按 UTC 整点每小时触发；启动时等待下一个整点，不立即额外扫描。一次运行中不再启动并行的下一轮；如果上一轮超时或仍在恢复，则先完成/记录当前轮再进入下一轮。

通过 PostgreSQL advisory lock 选择唯一的活动扫描执行者，并以整点扫描时段作为持久化运行键，避免多个后端实例对同一时段重复扫描。进程在一轮中途退出时，下一活动执行者读取已有逐币状态，只补做未完成币种；停机期间完全错过的时段不追溯补跑。

每次扫描开始时只读取一次 Watchlist 快照及 revision。对快照中的币种使用有界并发，单币失败写入该币种结果状态并继续；限制每个币种的工具调用轮数、请求超时和总扫描时间，避免 100 个 Watchlist 项加深查请求造成失控。若一个扫描周期无法按时完成，记录未完成状态而不启动重叠扫描。

备选方案是在前端轮询时触发扫描；这依赖用户持续打开页面，且多个浏览器容易重复调用，因此使用服务端调度。备选方案是无共享锁地在每个后端实例启动 ticker；多实例会造成重复模型费用、数据库记录和通知，因此用共享 PostgreSQL 锁和运行时段键协调。

### 2. 扩展模型协议并隔离只读行情工具

将模型 provider 扩展为能够发送 OpenAI-compatible tool definitions、解析 assistant tool calls、追加工具结果并继续调用，直到模型给出一个最终结构化结果或达到轮次上限。工具执行器仅注册 K 线与 OI 查询；调用上下文由服务端绑定本次 symbol，模型参数中不接受 symbol。周期及 limit 必须经服务端白名单和上限校验，所有工具只读，不提供订单、账户或 Watchlist 写入能力。

首次请求包含当前币种最近最多 100 根 OHLCV、结构化指标、支撑阻力以及精简的可用 OI 摘要和时间。K 线当前支持的 USDⓈ-M 周期可作为工具查询范围；OI 工具只公布 `5m`、`15m`、`30m`、`1h`、`2h`、`4h`、`6h`、`12h`、`1d` 等实际上游支持的周期。模型可以不调用工具，也可以自行选择一个或多个周期进一步确认。工具结果随结果记录保存为精简 evidence entries（工具名、周期、时间范围/采样时间、关键摘要），不保存逐条对话 transcript。

模型在一轮最终答复中以同一证据集比较左侧（确认前预判反转）与右侧（突破、回踩或结构确认后跟随）候选，并只返回更有证据的一套；如果两侧皆不清晰，返回 `wait` 状态。结构化 parser 按状态分别校验：可执行结果必须具备 Long/Short、有效入场/止盈/止损和价位关系；等待确认结果不允许带伪造的交易价位。UI 使用 `setup_timing` 替换原分析时间标签；数据快照时间和工具实际使用周期仍保留独立字段。

备选方案是只靠长 system prompt 要求模型“查询”数据；没有真实工具结果时模型可能猜测 OI，因此采用服务端执行工具调用。备选方案是固定所有数据周期；由模型选择支持周期符合需求且可避免每个币种无差别请求全部周期。若配置的 OpenAI-compatible 服务不支持工具调用，服务 SHALL 记录 provider/tool capability 错误，不把缺失工具数据伪称为已查询；初始摘要仍是本次 AI 可见证据。

### 3. 使用追加式扫描历史和独立投递 outbox

在现有嵌入式迁移机制中增加下一版本 PostgreSQL migration。至少包含：

- 扫描运行表：扫描时段、开始/结束时间、Watchlist revision、运行状态与计数。
- 逐币扫描结果表：每轮每币一行，唯一键为 `(run_id, symbol)`；保存最终状态、结构化分析 JSONB、confidence、左/右/等待标签、K 线数据时间、AI 使用周期、模型标识和 evidence summary。失败时保存错误类别，不伪装成成功结果。对扫描历史不自动清理。
- 通知 outbox 表：关联逐币结果，保存去重 fingerprint、通知状态、尝试次数、下次可尝试时间、企微响应码和成功时间。Webhook URL 只从服务端环境配置读取，永不写数据库。

每个最终分析先写入逐币历史，再按可执行状态和 `confidence > 70` 决定是否创建通知 outbox 项。低置信度、等待确认、AI/行情失败仍各自有逐币记录。结果行不被后续轮覆盖；投递状态和重试状态保存在 outbox 中，避免为了标记投递成功而改写原始分析。

将成功发送的 `setup_timing`、direction、方案周期、entry type 以及价格阈值用于去重。方向/时机/周期/入场方式改变会产生新方案；在其它字段相同时，入场、止盈或止损任一价格与上次成功通知相比偏移达到 `0.5 × 当前方案周期 ATR` 视为实质变化。置信度仅在跨越 70 门槛时使信号重新合格，不以小幅分数波动重复通知。首次合格或从不合格重新合格时生成新投递。文本变化本身不参与 fingerprint。

备选方案是只保存最新一条逐币分析；这不能满足“每次结果都落库”或回看逐轮变化的需求。备选方案是把扫描结果与企微发送状态写在同一行；Webhook 是外部非事务服务，分离 outbox 能保留每次不可变分析并独立处理投递。保留完整扫描历史会持续增长，但逐币最终 JSON 和短 evidence 摘要远小于每轮复制全部 K 线；后续若需清理，由单独的留存策略变更定义，而不是首版隐式删除。

### 4. 使用纯文本企微 webhook notifier

增加服务端可选的 `WECOM_WEBHOOK_URL` 配置及独立 notifier。消息采用参考项目的 text webhook JSON 格式，只从服务端向企微 POST；检查 HTTP 状态、合法 JSON 和 `errcode == 0`。日志仅记录经过脱敏的 endpoint 标识、状态码及错误类别，不记录完整 URL、密钥、模型 prompt 或工具请求凭据。

将同一轮新/变化的合格方案按置信度降序汇总成摘要。正文在 2048 UTF-8 字节上限内按完整方案块分片，使用纯文本而非 Markdown，每个方案保留币种、左/右、方向、置信度、周期、关键价格、简要依据和行情时间。空候选不发空消息。以每分钟最多 20 条做客户端限流，并独立保存每片投递状态。

只有企微 JSON `errcode == 0` 才标记 outbox 项成功并影响后续去重；明确失败的项使用有界退避重试。Webhook 缺失时保留待处理/未配置状态，分析扫描和结果历史继续运行。对端可能已经受理但本地超时的请求无法由 webhook 协议提供 exactly-once 保证；实现采用有界重试并记录 attempt 状态，接受极少数不确定投递可能重复的风险。

备选方案是发送 Markdown 以突出排版；参考实现记录了微信端 Markdown 展示不可靠，因此采用纯文本。备选方案是每币发一条消息；按每轮汇总更可读且减少速率占用，超长时再按完整币种方案拆分。

### 5. 保持配置和服务启动可恢复

调度分析沿用现有服务端 AI Chat 模型配置；企微凭据单独由 `WECOM_WEBHOOK_URL` 提供。未配置 Webhook 不阻断分析；模型未配置时不启动可生成结果的扫描任务，并明确记录功能未启用。增加扫描启停配置以便运维暂停费用型任务；Webhook 失败不会退出 HTTP 服务。

备选方案是将 webhook URL 放入数据库或前端设置；这些位置会扩大凭据可见面，故只在服务端环境中配置。备选方案是把后台调度作为独立进程，本仓库当前以单一 Go server 为部署入口，首版复用同一生命周期并通过数据库锁支持多副本。

## Risks / Trade-offs

- [每小时最多扫描 100 个币种且工具调用增加 token 和上游负载] → 对 symbol 并发、单次工具轮数、HTTP 超时和单轮总时长设置上限，并在扫描结果中保留调用次数及失败状态。
- [OpenAI-compatible 服务对 tool calling 的支持不一致] → 用本地 HTTP 行为测试覆盖 tool call 协议；运行时把不支持/无效 tool call 记录为失败，不伪造上下文。
- [无限期保存每个扫描结果会持续增加 PostgreSQL 存储] → 只持久化结构化最终结果和证据摘要，不复制完整历史 K 线或中间消息；不擅自删除用户要求保留的生成结果。
- [Webhook 接收成功但响应丢失时可能重复发送] → 使用 outbox 状态、投递结果校验和有界重试，清楚记录不确定尝试；企微接口不提供端到端幂等保证。
- [AI 置信度并非胜率，且模型可能误判结构] → 在 UI 和企微正文显式标明其为信号强弱，校验可执行价位关系，等待确认状态永不进入交易方案通知。
- [企微限制正文长度与请求速率] → 按 UTF-8 字节在方案块边界分片，并对分片单独限流与记录结果。
- [自动任务多副本运行导致重复调用] → 使用 PostgreSQL advisory lock 和每小时运行时段唯一键协调扫描所有者。

## Migration Plan

1. 增加向前兼容的 PostgreSQL migration：创建扫描运行、逐币结果和通知 outbox 表及查询索引；不改写现有 Watchlist 数据。
2. 先部署数据库迁移和后端能力，配置 `WECOM_WEBHOOK_URL` 与扫描启停变量；Webhook 缺失时可以先验证扫描结果落库。
3. 使用本地 HTTP 模拟器验证模型 tool call 和企微响应码/异常路径；再启用有限 Watchlist 实例验证整轮扫描、数据库历史、去重和实际群消息。
4. 回滚时关闭扫描开关并移除 Webhook 配置，HTTP 服务和 Watchlist 仍可使用。迁移表与既有历史保留；不自动删除任何已生成结果或回滚数据库中的分析历史。
