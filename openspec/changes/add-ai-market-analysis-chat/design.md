## Context

动机与用户可见范围见 [proposal.md](proposal.md)，可观察行为见本变更的 `ai-market-analysis-chat` 与 `chart-analysis-display` delta specs。

Dashboard 当前在同一页面协调所选交易对、周期、REST K 线与指标请求、K 线 SSE 和独立的 Watchlist 报价流；Watchlist 修改与图表选择均会更新当前标的。后端已有交易对和周期校验、K 线获取及指标分析服务，但没有模型 provider 或对话 API。新对话必须使用服务端可信的行情上下文，不能依赖浏览器提交的指标结果，也不能把模型密钥发送到浏览器。

## Goals / Non-Goals

**Goals:**

- 保持 K 线作为主要区域，将 Watchlist 与 AI 对话组合进右侧同一侧栏，并在窄屏下按图表、侧栏顺序排列。
- 从同一份 K 线快照计算结构化指标并构建模型上下文，确保回答中的标的、周期和数据时间一致。
- 使用可替换的模型 provider 边界和服务端配置，避免新增 SDK 依赖或将凭据放入客户端。
- 将多轮会话保存在浏览器运行期间并按交易对隔离；服务端不持久化聊天记录。

**Non-Goals:**

- 不恢复已退役的静态技术分析面板或交易机会功能。
- 不在首版加入交易执行、Watchlist 写操作、跨交易对自主扫描或后台定时问答。
- 不将聊天历史写入数据库或浏览器持久存储，也不要求服务端保存会话状态。

## Decisions

### 1. 右侧使用单一双 Tab 侧栏

将 Dashboard 主内容改为桌面端两列：左侧图表占用剩余宽度，右侧侧栏使用约 320–400px 的受限宽度；当可用宽度不足以保证图表和侧栏可读时改为纵向排列，并让图表先于侧栏。默认选中 Watchlist，以保留打开页面后的现有入口。

侧栏内部以两个 Tab 显示 Watchlist 和 AI 行情分析。Watchlist 的报价 SSE 仍由 Dashboard 生命周期管理，不随 Tab 显隐停止；两侧栏视图切换时保留当前会话消息。聊天消息区独立滚动，输入区固定在面板底部。图表继续由原图表组件占据主区域，不移动行情状态协调逻辑。

备选方案是保留左侧 Watchlist 再单独新增第三栏；在常见桌面宽度下这会挤压图表，且不符合用户提出的共享容器和两个 Tab。

### 2. 每个用户回合由后端生成可信的行情上下文

新增 `POST /api/analysis/chat`。请求携带当前 `symbol`、`interval`、当前币种最近的用户/助手对话和新问题；不接收客户端生成的指标或 K 线作为可信输入。handler 使用现有交易对及周期校验，再调用行情上下文服务读取最多 100 根最新 K 线，并从同一份 K 线计算现有结构化分析结果。为避免 K 线和指标来自不同时间点，分析计算应能消费已读取的 K 线，而不是再次独立拉取一份数据。

上下文服务将标的、周期、最新 K 线时间、K 线样本和现有指标/结构化分析交给对话服务。模型成功响应后，API 返回完整回答及上下文数据时间。若 K 线不足、上游获取失败或分析上下文不可用，则在调用模型前返回清晰错误。

备选方案是直接把 Dashboard 的 `analysisResult` 和当前蜡烛数组发到后端；客户端数据可能因切换、旧响应或请求构造错误而与服务器当前选择不一致，因此只发送标的、周期与对话文本。

### 3. 使用无状态对话 API 和内存会话

前端在 Dashboard 生命周期内按交易对维护消息列表。币种切换时切换到相应列表；周期变化不清除列表。每次发送时捕获币种和周期，并将回复写回该币种的原始会话，从而防止切换期间返回的旧回复串入当前币种。页面重载或关闭后清空会话。

后端每次请求均重新获取行情上下文；前端只发送最近的对话轮次和当前问题供模型理解，完整显示记录仍留在内存中。首版使用普通 HTTP 请求并在完整回答返回后显示，不增加流式协议或服务端会话存储。

备选方案是由后端维护会话 ID 和历史记录；这需要数据库或过期策略，超出按浏览器会话保存的首版范围。另一备选方案是模型流式输出；完整回答响应能先满足对话能力，同时避免新增中断、部分消息及 SSE 协议状态处理。

### 4. 服务端封装 OpenAI-compatible provider

定义模型 provider 接口并在后端配置模型 API URL、模型名称和密钥。首版使用 Go 标准 HTTP 客户端实现 OpenAI-compatible Chat Completions 请求/响应适配，不引入模型 SDK；以超时和最大输入消息数限制单次调用。API 错误转成不含凭据或上游敏感响应正文的通用错误；排障日志只记录状态和可定位的错误类别，不记录 API Key、完整聊天内容或行情上下文。

handler 构造和对话服务注入 provider，使行为测试可用本地假 provider 覆盖成功、拒绝和超时路径。provider 未配置时，用户提交后得到明确的可恢复错误；切换 Tab 不调用模型。

备选方案是将特定模型厂商 SDK 直接嵌入 handler；当前没有既有 AI SDK，直接绑定厂商会扩大依赖和迁移成本。浏览器直连模型服务会暴露密钥，故禁止。

### 5. 保留前端行情状态协调边界

Store 继续持有当前交易对、周期、K 线、分析状态和价格流；对话状态只保存短期聊天记录，不改写行情状态。发起回复前记录交易对和请求代次，完成后按原币种归档；Dashboard 的选币及周期协调仍负责图表重载和 SSE 切换。AI 请求失败不清空历史，也不改变实时/备用行情状态。

### 6. 使用经过验证的数据结构渲染方向分析卡片

模型只输出 JSON 字段：`direction`、`entry_type`、`entry_price`、`take_profit`、`stop_loss`、`confidence`、`leverage` 和 `analysis`。后端解析并校验必填值、数值范围及 Long/Short 对应的入场、止盈、止损顺序；无效响应作为模型失败返回，不把任意原文当成结构化成功结果。前端用 API 返回的结构化对象渲染卡片，并以规范化 JSON 作为后续对话历史。

POC 不能由现有 OHLCV K 线精确还原，因此从同一快照中选成交量最大的 K 线，以 `(high + low + close) / 3` 提供估算值并显式标注“估算”。支撑/阻力从现有分析价位中按最新收盘价筛选最近的下方支撑和上方阻力；缺失值以空值返回，由 UI 显示“未识别”。这些关键价位由服务端快照确定，不使用模型生成的价格覆盖。

分析时间取前端收到成功回复时的本地时间，行情数据时间仍使用后端最新 K 线时间。保证金亏损比例由前端根据有效入场价、止损价与杠杆计算：`abs(entry - stop) / entry * leverage * 100`；说明该近似值不含手续费、滑点和资金费率。卡片只呈现只读分析，不连接订单执行。

## Risks / Trade-offs

- [模型回答可能误读或过度推断指标] → 每轮请求提供同一快照的行情、结构化指标和时间，提示词限定回答范围；界面标示数据周期和时间，不把连接成功当作数据新鲜。
- [模型 provider 协议虽兼容但响应细节不同] → 隔离 HTTP 适配层，以可配置 endpoint 和模型名部署，并使用本地 HTTP 假服务覆盖协议成功和错误解析。
- [后端为每个问题重新取行情会增加上游请求耗时] → 只在用户提交问题时取数，限制 K 线样本数；不因打开 Tab 或收到行情推送自动触发模型调用。
- [小屏或长对话压缩图表空间] → 设置图表与侧栏的最小可读宽度，低于阈值后纵向排列；消息区单独滚动并固定输入区。
- [用户快速切换标的时回复返回较晚] → 将请求结果按发起时捕获的标的及会话归档，禁止写入新选中的标的对话。

## Migration Plan

1. 增加服务端模型配置；未配置模型时行情与 Watchlist 功能保持可用，聊天提交显示可恢复的未配置状态。
2. 先增加 Dashboard 布局、会话隔离、请求切换和失败状态的行为测试，再实现前端双 Tab 与对话状态。
3. 先增加行情上下文及 provider 的本地 HTTP 行为测试，再实现对话 API、上下文聚合和 provider 调用。
4. 运行相关前后端回归、前端类型检查及构建；验证本地假 provider 的请求与错误路径及真实浏览器中的响应式布局。真实模型凭据不可用时，将真实 provider 验收标记为未验证。

回滚时可移除聊天 Tab、聊天 API 路由和模型配置；行情与 Watchlist 不依赖模型服务，也没有数据库迁移或持久会话需要回滚。
